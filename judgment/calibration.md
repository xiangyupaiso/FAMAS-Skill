# 决策日志季度校准

> 数据大家都能接，**校准记录不能**。这是从"会写报告"到"有专业度"的分水岭，也是最难被复制的部分。

## 一、什么时候写日志

每次 `synthesis` 产出结论后，若用户授权本地持久化，按 `judgment/decision-log.schema.json` 写一条记录：假设、证据引用、反证引用、置信度上限、结论、失效条件、回看日期。**默认不写**（`privacy.user_authorized = false`），未授权时只在本次会话内保留。

## 二、季度校准六步

```
1 取回     按 review_due 取出到期的 decision_log 记录
2 补数据   重新取同一标的的当前事实（performance_metrics / periodic_report_reader）
3 核对     逐条检查：原假设是否成立、失效条件是否触发、结论与实际观测偏离多少
4 归因     把偏差归到三层之一：数据层 / 口径层 / 框架层
5 更新     修订后续判断的失效条件、置信度上限与反证检查重点
6 留痕     写回 calibration_notes 与 error_layer，不改写原始结论
```

**禁止改写原始结论**。校准的价值在于保留"当时怎么想的"，改掉就没有可回看的对象了。

## 三、误差三层归因

| 层 | 典型原因 | 修正动作 |
|---|---|---|
| 数据层 | 字段缺失、季报滞后、多源分歧未解释、用估算值当实测 | 补 `missing_fields` 规则、加交叉校验源 |
| 口径层 | 复权方式、报告期、份额类别、样本窗口、基准选错 | 统一 `data/semantic-fields.yaml` 口径并回写 |
| 框架层 | 假设过强、反证不足、置信度上限偏高、否决项阈值太松 | 更新 `judgment/framework.md` 与 `veto-rules.yaml` |

一次校准若只归到"看错方向"，视为未完成——那不是可操作的结论。

## 四、更新规则

- `error_layer = framework` 且连续两次出现 → 提高 `devils_advocate` 对应模式的检查强度
- 失效条件频繁提前触发 → 收紧 `veto-rules.yaml` 阈值
- 多源分歧反复出现 → 在 `policies/source-trust.md` 的冲突表增加该字段的口径说明
- 所有更新都要留 changelog，不静默调参

## 五、隐私与边界

- 本地持久化需用户显式授权；默认 `local_only: true`，不上传、不入库、不进仓库
- 日志只含判断过程，不含用户身份、账户、持仓金额等非必要信息
- 校准报告不构成投资建议，不评价用户决策，不给操作指令
- 输出前仍须经过 `policies/compliance.md` 检查清单
